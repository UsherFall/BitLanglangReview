# 包含性闸门：改动前基线与实测口径

> 本文件是 `prd.md` AC4 的对照基线，也是实现阶段判断"行为变更幅度是否属预期"的依据。
> 复现命令（仓库根目录，只读行情、不写数据库）：
> ```bash
> node --experimental-transform-types .trellis/tasks/09-20-shrink-containment-breakout/research/containment-impact-probe.mjs
> ```

## 1. 为什么要做这个测量

改动前必须回答两个问题，否则计划里的验收标准没有标尺：

1. 包含性闸门是否真的从不触发？
2. 让它真正生效之后，扫描结果会变多少？

## 2. 方法

- 池：币安 USDT 永续按 24h 成交额降序取 Top60（仅 `crypto` scope，`isScannable` 过滤），与 `CoinScanService` 的选池规则一致。
- 窗口：每个 (品种, 周期) 取 `limit=100` 根，按 `timestamp + step <= anchor` 丢掉未收盘那根，与 `coin-scan-service.ts:122` 一致。
- 判定：镜像 `detectConvergence` 的循环，唯一差别是把"确认区间留出的末尾根数"参数化（`excludeTail`）。`excludeTail = 0` 即改动前行为（区间含最新一根）。
- 合格口径：`detectConvergence` 返回非 null 且 `score >= 0.6`（UI 默认 `minScore`），与面板一致。

## 3. 实测结果

### 3.1 改动前：包含性闸门从不触发

| 周期 | 候选带总数 | 平坦度拒绝 | 收缩度拒绝 | **包含性拒绝** | 通过 |
| --- | --- | --- | --- | --- | --- |
| 5m | 5700 | 905 | 828 | **0** | 967 |
| 15m | 5700 | 1689 | 426 | **0** | 585 |
| 1H | 5700 | 1632 | 746 | **0** | 322 |
| 4H | 5685 | 2137 | 349 | **0** | 207 |
| 1D | 5523 | 1661 | 764 | **0** | 187 |

全周期合计 **28200 个候选带，包含性拒绝 0 次**。主拦截者是**平坦度**（8024 次），其次是收缩度（3113 次）。

原因：带必然包含最新一根，而真实K线的 `close` 必在自己的 `[low, high]` 内，所以
`min(band.low) <= lastPrice <= max(band.high)` 恒成立，`±10%` 容差是空转。

## 4. 对验收的结论

- **`excludeTail = 1` 的破坏面极小**：包含性闸门真实触发（98~107 次），但在榜币数与合格(币×周期)数基本不变。
- 所以本任务的收益是**语义正确 + 被测覆盖**，而不是筛选力提升。这一点必须如实写进结论，避免后来者误以为"修完榜单会大改"。
- **AC4 的可接受区间**：`包含性拒绝 > 0`；在榜币数 27 ± 1；合格(币×周期)数 44 ± 2。

## 5. 另一个关键事实（决定改动不越界）

在改动前，**"突破的币掉榜"这件事是成立的**，但由平坦度而非包含性负责。证据：在一段"16 波动 + 16 安静"（基准下 12 条候选带通过，score 0.796~0.890）之后追加一根**合法**的向上突破K线（`low=100, high=131, close=130`），12 条候选带全部被**平坦度**拒绝（`drift` 0.099~0.229，而 `flatTol = 2 × runMed = 0.020`）。

这解释了为什么本次修复的量化影响很小：真正的突破早就被平坦度拦住了，包含性只是补上"语义归属 + 轻微突破的兜底"。
