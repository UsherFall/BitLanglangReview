# 技术设计：包含性闸门真正生效

## 1. 边界

- **改动层**：仅 `src/domain`（纯函数，无 React / fs / SQLite / fetch）+ `tests/`。
- **改动文件**：`src/domain/coin-scan.ts`（唯一生产代码文件）、`tests/coin-scan.test.ts`。
- **不改动**：`src/server/coin-scan-service.ts`、`src/ui/*`、`tests/coin-scan-service.test.ts`（预计不需改，见 §6）、所有 API 契约。
- **前置约束**：`src/domain` 不得引入任何 I/O；本次改动是纯计算，天然满足。

## 2. 缺陷的形式化

设窗口内已排序K线 `c[0..last]`，`last = n - 1`。候选带 `band = c[start..last]`，长度 `runLen = last - start + 1`。

现行代码（`:264-267`）：

```
rangeLow  = min(band.low)
rangeHigh = max(band.high)
tolerance = 0.1 * (rangeHigh - rangeLow)
reject if lastPrice < rangeLow - tolerance or lastPrice > rangeHigh + tolerance
```

因为 `c[last] ∈ band`，且真实K线满足 `c[last].low <= c[last].close <= c[last].high`：

```
min(band.low) <= c[last].low <= lastPrice <= c[last].high <= max(band.high)
```

故 `rangeLow <= lastPrice <= rangeHigh` 恒成立，`reject` 分支不可达。**缺陷性质：判定基准包含被判定对象。**

## 3. 选定方案

**确认区间（confirmed range）由带内前 `runLen - 1` 根构成，即把最新一根从区间里排除出去。**

```ts
// 新增可命名常量（模块级）
const CONVERGENCE_CONFIRMED_TAIL = 1;

// 循环内：
const confirmed = band.slice(0, band.length - CONVERGENCE_CONFIRMED_TAIL);
const rangeLow  = Math.min(...confirmed.map((c) => c.low));
const rangeHigh = Math.max(...confirmed.map((c) => c.high));
const tolerance = 0.1 * (rangeHigh - rangeLow);
if (lastPrice < rangeLow - tolerance || lastPrice > rangeHigh + tolerance) continue;
```

`position` 复用同一组 `rangeLow / rangeHigh`（R5/AC6）。

### 3.1 为什么"排除最新一根"是唯一能生效的口径

任何"拿带自身成员当基准"的判据都不可达（§2 的不等式对带内任意成员都成立）。要让包含性有意义，基准集合必须与被判定对象**不相交**。因为带被钉死为"结尾 = 最新一根"，被判定对象只能是那一根，所以基准集合只能是 `band \ {c[last]}`。这不是取舍，是被约束推出的唯一解。

### 3.2 为什么"波动率指标"不跟着改（R3）

两者对"最新一根"的需求正好相反，这是有原则的区分：

| 判据 | 是否含最新一根 | 理由 |
| --- | --- | --- |
| `runMed` / `preMed` / 平坦度 `edgeDrift` | **含** | 这些是"现在有多安静"的**度量**。最新一根如果不安静，就应该被度量出来，从而拒绝。 |
| 确认区间（包含性 + `position`） | **不含** | 这是"价格是否已离开区间"的**判定基准**。基准包含被判定对象就恒真。 |

保持 `runMed`/平坦度不变还有一个直接收益：**通过的带分数不变**（score 只由 `runMed/preMed/runLen` 决定），所以本次改动的影响面被限制为"拒绝更多"，而不是"所有分数重算"。这让 AC4 可测量、可解释。

### 3.3 突破根必然被全部候选带拒绝（重要推论）

对任意 `runLen`，确认区间 = 带内除最后一根之外的全部K线。当最后一根是真正的向上突破（其 high 高于此前所有K线）时，`lastPrice` 必然高于任一确认区间的 `rangeHigh`，于是**每一条走到包含性闸门的候选带都被拒绝**（更早的平坦度 / 收缩度闸门可能先把它拦下，闸门顺序不变），该周期返回 `null`。

这正是"扫的是收敛、不是突破"的正确编码：突破的币明确出局，且由包含性闸门负责（而不是像现在这样靠平坦度误打误撞）。

## 5. 边界条件与失败模式

| 情形 | 行为 | 判定 |
| --- | --- | --- |
| `runLen = minRun = 5` | 确认区间 = 4 根。合法，且 ≥ 2 根。 | 正常 |
| 有人把 `minRun` 覆盖成 < 2 | 确认区间为空 → `Math.min(...[]) = Infinity`、`Math.max(...[]) = -Infinity` → `tolerance = -Infinity` → 比较结果恒为 `reject`。 | **失败方向安全**（拒绝而非放过），且不抛异常。不额外加分支（该覆盖在仓库中不存在）。 |
| 确认区间内 4 根完全同价 | `rangeHeight = 0` → `tolerance = 0`；`position` 走既有 `rangeHeight > 0 ? … : 0.5` 分支。 | 行为不变 |
| 窗口内存在 `low <= 0` | 已由 `:238` 的全窗口守卫提前 `return null`，与本次改动无关。 | 不变 |
| 带长 = 5、确认 4 根，`lastPrice` 恰好等于边界 | 用 `± tolerance` 的闭区间语义（`<` / `>` 才拒绝），与现行代码一致。 | 不变 |

## 6. 对既有测试的影响（已预判）

- `tests/coin-scan.test.ts:76`「containment gate」用例**必须重写**：夹具 `high: 100.5 / close: 130` 是非法K线（AC2）。
  - **规划期的预测在此更正**：曾预判"改动后该用例会失败"，实测不成立——它**继续通过**，因为在改动前的口径下整带区间是 `[99.5, 100.5]`、允许上界 `100.6`，而那根非法 `close = 130` 确实越界，闸门真的触发了。所以它不是"假绿"，而是"只在不可能输入下可达"。重写的意义是让它在**合法K线**上守住同样的行为（否则该断言随时可能被合法数据绕过）。
- `tests/coin-scan.test.ts` 其余用例的夹具是**等宽K线**（`[99.5, 100.5]`、`[98, 102]`、`[49, 51]`），带内每根同形 → 最新一根必然落在确认区间内 → 行为不变。预计全部保持通过。
- `tests/coin-scan.service.test.ts` 的 `strongBars` / `weakBars` 同样是"16 波动 + 16 等宽"，`uptrendBars` 由平坦度拒绝。预计不需改动；实现后必须实跑确认（`implement.md` 步骤 4）。

## 7. 被否决的备选方案

| 备选 | 内容 | 否决理由 |
| --- | --- | --- |
| A · 标记化 | 允许突破的币留在榜上，新增"已突破"标记 | 用户明确："我们这里扫的是收敛，不是扫突破的"。把已突破的币混进收敛榜会污染榜单语义。 |
| B · 允许带结束在最近 N 根内 | 扩大候选带搜索空间，可发现"3 天前结束的带" | 改变"带"的定义 → 全部候选带与分数重算，且引入"最近发生过收敛"的过去时语义，与"当下状态"榜单混合。超出本次范围（列入 Non-Goals）。 |
| C · 用对照段（`preStart..start-1`）划区间 | 要求价格落在**前段**的区间内 | 语义错位：收敛的正确图景是"带比前段更窄"，价格完全可以落在前段区间的中间偏下位置。用前段区间会变成另一种不相关的过滤。 |
| D · 直接删掉包含性闸门 | 承认平坦度已兜底，删掉死代码 | 用户的诉求是"让包含性生效"。删掉会让"突破保护"彻底没有归属，也让这套判定失去一层显式语义。 |
| E · 同时调 10% 容差 | 把容差收紧以增强筛选力 | 会把两个变量混在一次改动里，无法归因；容差标定应以闸门生效后的真实数据另行决策（列入 Open Questions）。 |

## 8. 兼容性与回滚

- **无持久化状态**：不写数据库、不改缓存键。已有的 `candles` 表不受影响。
- **无迁移**：纯函数行为变更。
- **回滚**：`git revert` 该文件即可；唯一的连带影响是 `tests/coin-scan.test.ts` 的用例需一并回滚。无外部依赖。
- **可观测差异**：扫描结果会少 0~2 个"币×周期"合格项（实测），在榜币数不变。无新增日志/告警。

## 9. 测试策略

1. **AC1 行为契约（必做）**：夹具 = 16 波动根 `[94, 100]` + 15 安静根 `[99.5, 100.5]` + 1 根末根；控制组末根取 `[99.5, 100.5]`（断言非 `null`），突破组末根取 `[100, 101.5]`（中点收盘 100.75，断言 `null`）。两组只差末根一根。
   - 平坦度余量已核算（长带 runLen=16）：`drift(low) 0.001662`、`drift(high) 0.003290`、`flatTol = 2 × runMed = 0.02010` → **余量 6.1 倍**；收缩度也通过（`runMed 0.01005 < 0.9 × preMed = 0.9 × 0.06383 = 0.05745`）。故长带被拒的唯一可能原因就是包含性。
   - 实测：突破组在改动前返回 `score 0.8898`（非 null），改动后返回 `null`，且 6 条进入到包含性闸门的候选带被**全部**拒绝（`6/6`）。§3.3 的推论得到验证。
2. **AC2 合法性（必做）**：删除 `:79-84` 的非法夹具，改为合法 OHLC。审计范围限定在 `tests/coin-scan.test.ts` 与 `tests/coin-scan-service.test.ts`（唯一两个把夹具喂给检测器的文件）；两个文件的助手都取 `close = (low + high) / 2`，天然合法。
3. **AC5 防误伤（必做）**：现有"通过平坦度+收缩度"的用例（`:38`）、"无收缩则 null"（`:54`）、"弱收缩分数低于阈值"（`:61`）、"趋势通道 null"（`:163`）全部保持通过；校准常量断言用例（`:175`）保持通过。
4. **AC6 直接证据（已实现）**：规划期设想的"末根向下小破 → `position === 0`"**不可行**——末根若是整条带的极值，旧口径下的 `position` 也已经接近 0/1，两种口径无法区分。改用**对称插针**：末根取 `[99.3, 100.9]`（中点收盘 100.1，仍在确认区间 `[99.5, 100.5]` 的容差内，band 存活）。此时
   - 确认区间口径：`(100.1 - 99.5) / (100.5 - 99.5) = 0.6`
   - 整带区间口径：`(100.1 - 99.3) / (100.9 - 99.3) = 0.5`
   断言 `position ≈ 0.6` 即可锁住"只读确认区间"。实测 `position = 0.6000`。
5. **AC4 真实数据复测（必做）**：改成动后重跑镜像探针（Top60 加密池 × 5 周期 × `minScore 0.6`），把"在榜币数 / 合格(币×周期)数 / 包含性拒绝次数"写入 `research/`。
