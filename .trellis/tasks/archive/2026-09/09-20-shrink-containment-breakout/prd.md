# 收敛扫描：修正包含性闸门与突破处理

## Goal

让 `detectConvergence` 的**包含性闸门真正生效**：判断"最新一根收盘价是否已突破带"时，比较基准必须是"不包含最新一根"的区间。同时把注释与测试改成真实语义——现在是"注释承诺了一重突破保护，实现上从未触发"。

## Background（现状事实，均已实测）

`src/domain/coin-scan.ts:234` 的 `detectConvergence` 用一个滑动窗口搜索"波动率收敛带"。三条硬约束决定了候选带：

1. 带必须**结尾贴住最新一根已收盘K线**（`:244` `last`、`:252` `slice(start, last + 1)`）；
2. 带至少 `minRun = 5` 根（`:137`）；
3. 带前面必须有一段**等长**的对照段（`:250-251` `preStart < 0 → continue`）。

100 根窗口下：96 个起点里 46 个能算（带长 5~50），50 个因前面凑不出等长对照段被丢弃。

每条候选带按顺序过三道闸门（`:259` → `:262` → `:267`）：

| 闸门 | 位置 | 判定 |
| --- | --- | --- |
| 平坦度 | `:259` | `max(edgeDrift(low), edgeDrift(high)) > 2.0 × runMed` → 拒绝 |
| 收缩度 | `:262` | `runMed >= 0.9 × preMed` → 拒绝 |
| 包含性 | `:263-267` | 最新收盘超出 `[rangeLow, rangeHigh] ± 10%` → 拒绝 |

**问题：包含性闸门在真实数据上永不触发。**

因为带必然包含最新那一根，而一根真实K线的 `close` 必然落在自己的 `[low, high]` 内，所以：

```
rangeLow  = min(band.low)  <=  band[last].low   <=  band[last].close = lastPrice
rangeHigh = max(band.high) >=  band[last].high  >=  band[last].close = lastPrice
```

`lastPrice` 恒在 `[rangeLow, rangeHigh]` 内，10% 容差是空转。实测 60 币 × 5 周期，全周期合计 **包含性拒绝 0 次**（1D 单周期 5523 个候选带全部 0 次）。

**后果一（自欺）**：`:263-267` 的注释写着"a price that has broken out is no longer 蓄力"，但这条保护实际由**平坦度**兜底（突破那根把 high 序列的回归斜率撑高 → `drift` 超过 `2.0 × runMed`）。行为上"突破的币掉榜"成立，但责任写在错误的闸门上。

**后果二（测试只在非法输入下可达）**：`tests/coin-scan.test.ts:76` 有一条专门测这个闸门的用例，它构造的最后一根 K 线是 `high: 100.5` 但 `close: 130`。核算后可确认：改动前的闸门**确实**在这个夹具上触发了（整带区间 `[99.5, 100.5]`、容差 `0.1`、允许上界 `100.6`，收盘 `130` 越界）。问题不在"闸门没触发"，而在这个触发**依赖一根 `close` 越出自身 `[low, high]` 的不可能K线**——换成任何合法K线，闸门都不可达。所以该用例并没有守住它声称守住的行为。

**行为影响已实测**（Top60 加密池、窗口 100 根、minScore 0.6）：

| 留出末尾根数 | 在榜币数 | 合格(币×周期) | 包含性拒绝 |
| --- | --- | --- | --- |
| 0（现状） | 27 | 44 | 0 / 2299 |
| **1（本任务选定）** | **27** | **43** | **107 / 2299** |

即：修复后榜单几乎不变（在榜币不变，合格数少 1）。本任务的收益是**语义正确与被测覆盖**，不是筛选力提升。

## Requirements

- **R1**：包含性闸门必须真正生效——判断最新一根是否突破时，比较区间必须由**不含该根**的K线构成。
- **R2**：确认区间取**带内前 `runLen - 1` 根**（即只留出最新一根）。该口径是可命名的常量，不允许散落字面量。
- **R3**：波动率类指标（`runMed`、`preMed`、平坦度的 `edgeDrift`）**继续用整条带**（含最新一根），本次不改。理由见 `design.md`：波动率要含最新一根才叫"现在也安静"，而区间判断的基准绝不能包含被判断的对象。
- **R4**：突破容差保持 `10% × 区间高度`，本次不调参（但需在注释中说明它首次真正生效）。
- **R5**：`position` 与闸门共用**同一个区间**（确认区间），避免出现两套区间口径。
- **R6**：注释必须改成真实语义：明确"闸门负责突破保护"、"区间排除最新一根的原因"、以及"平坦度是另一道独立的闸门"。
- **R7**：测试改造——删除依赖非法K线的用例；新增能证明"闸门单独负责"的用例（平坦度与收缩度都通过，仅因突破被拒）。
- **R8**：不得改动——扫描窗口（加密 100 / 会话类 200）、`minScore` 默认 0.6、评分公式与权重、三道闸门的阈值常量、选品池规则、API 字段名与结构、前端。

## Non-Goals

- 不改前端（用户明确：不需要在结果里区分"带内/已突破"）。
- 不处理"长度项在日线上失效"（`lengthScale = 16` 相对 100 根窗口过小）。
- 不处理"新币前置段被上市初期行情污染"。
- 不处理"锚定最后一根导致榜单抖动"。
- 不允许带结束在最新一根之前（搜索空间不变）。
- 不做"标记化"输出（不新增字段、不把突破作为事件透出）。
- 不改 `10%` 容差、`minRun`、`flatRatio`、`convergenceRatio` 的取值。

## Open Questions

- `10%` 容差在闸门真正生效后是否合适——**本次保留不动**，留待后续用真实数据标定（已列入 Non-Goals）。
- `position` 口径变化对未来的 UI 展示意味着什么——**check 阶段两处更正**：
  1. 「无消费者」的判断是错的。确有一处消费者：`src/ui/CoinScanPanel.tsx:310` 把 `position` 以百分比展示在展开详情表的「位置」列（经 `formatPosition`，`:362`）。原文点名的 `src/ui/coin-scan-results.tsx` 在仓库中不存在，此前的核对因此误判。
  2. 影响不是"小幅漂移"。实测（`research/containment-delta.md` 末节，同一时点 41 条合格行）：**36 条显示值不变、5 条变化**，平均 Δ 1.37 个百分点、**最大 Δ 25.4 个百分点**，且个别行会显示 `0%`/`100%`（最新一根越过确认区间但未超 10% 容差，被既有的 `clamp01` 压到端点）。
  - **已确认（用户决定）**：**保持统一口径**。接受这 5 行显示值变化（含端点值），换取"代码只有一套区间、语义一致"。`position` 继续与闸门共用确认区间，实现无需调整；不采用"position 回到整带区间"（会产生两套区间、AC6 失效），也不采用"统一口径且去掉 `clamp01`"（会突破 `0~1` 的字段契约）。
