# 复盘看当时的市场热度

## Goal

复盘（交割单复盘 / Bitget 订单复盘）单笔交易时，能判断「当时市场场子热不热」：面板以该笔交易的入场/离场时刻为锚点，用 Binance USDT-M 主流标的池的 24h 涨跌分布合成一个 5 档市场温度结论，并列出当时涨/跌得最凶的币及成交额。

用户价值：复盘不再只盯自己的单子，还能回答「这笔单发生在普涨的热闹行情、还是普跌/分化的冷清行情」——判断是市场给机会还是自己逆势，让归因更准确。

### 随附的本任务范围（用户在澄清中追加）

- 全局共享保守限速器：把 scan 模块私有的 `scanPacer`（coin-scan-service.ts:52-65）上提为 Binance 全模块共享的请求节奏器，间隔调保守（~100-120ms ≈ 8-10 req/s），消除 scan/热度并发叠加触发 418。代价：scan 单次从 ~15s 变 ~30-36s。
- 删除「价格警报」功能（用户明确要求，同时减少 Binance 请求消费者）。

## Background（已确认事实与决策）

- 功能全新：代码 / CONTEXT.md / 任务历史中均无市场热度、涨跌榜、板块、人气实现。`龙头币(LeaderCoinPanel)` 只是本地手工标记列表，不识别异动。
- 历史 ticker（24h 涨跌、成交量）只在实时接口、从不落盘；唯一可追溯历史的是本地 K 线缓存（SQLite `candles` 表）+ 按需拉取历史 K 线。锚点时刻涨跌必须由 K 线现算。
- Binance klines 单次请求即覆盖任意老锚点的 [T−24h, T] 区间；每币 1 次请求，可行性成立。
- 复盘标的为 OKX SWAP（`BTC-USDT-SWAP`）与 Bitget（`BTCUSDT`）；热度池用 Binance USDT-M 命名（`BTCUSDT`）。复盘币纳入池中按基础资产归一。
- 面板先例：明细头部 `其他币`/`龙头` 浮层按钮（App.tsx:751-757）；服务端先例：`/api/scan?anchor=<ms>`（coin-scan-service.ts）。
- 限频现状（用户反馈 + 代码核实）：选币 scan 以 50ms 间隔（≈20 req/s）节奏、并发 5、单次最多 300 klines（coin-scan-service.ts:17,27）；行情告警 monitor 每 60s 一次全市场 ticker（weight 40，alert-monitor.ts:40,62）。即使节奏到 ~20 req/s，仍会偶发 Binance IP 封禁 418，封禁期 ≥2 分钟且期间请求会延长封禁（http.ts:63）。429/418 由全局 `binanceRateGate` 停发全管线（http.ts:105），429 自动退避、418 快速失败透出警告（feedback: 429 警告要显示、418 快速失败、不静默重试）。
- 价格警报功能范围（删除对象）：`src/domain/price-alert.ts`、`src/server/alert-store.ts`（表 `price_alerts`）、`src/server/alert-monitor.ts`、`src/server/notify.ts`（Server酱，仅警报使用）、`/api/alerts` 路由与 ServerChan 装配（app-plugin.ts:8-9,32,62-66,221-255）、选币面板「价格警报」区块与结果行「设警报」（CoinScanPanel.tsx）、App.tsx 相关 state 与 props、styles.css 警报样式、测试 `tests/alert-monitor.test.ts`、`tests/alert-store.test.ts`、`tests/price-alert.test.ts`、`tests/serverchan-notifier.test.ts`。

### 已确认产品决策

- 使用场景：交割单 + Bitget 订单复盘；入口在单笔交易明细头部；锚点 = 入场时刻，可切离场时刻。自由回溯、独立模块不做。
- 标的池：Binance USDT-M 当前 24h 成交额 Top-N（默认 80）+ 当前复盘币强制纳入；剔除稳定币报价对；复用 `isMarketOpen` 对带 `MarketClass` 的休市 TradFi 合约做「休市跳过」并上报数量（与 scan 的 Session Gating 同哲学）。
- 温度规则：**涨家占比（广度）+ 池中位涨跌幅合成 5 档**（门槛暂定，上线后标定）：

| 档位 | 判定 |
|---|---|
| 热市 | 涨家占比 ≥ 60% 且 中位涨跌 ≥ +1% |
| 偏热 | 涨家占比 ≥ 60% 或 中位涨跌 ≥ +1%（仅中一） |
| 中性 | 其余 |
| 偏冷 | 跌家占比 ≥ 60% 或 中位涨跌 ≤ −1%（仅中一） |
| 冷市 | 跌家占比 ≥ 60% 且 中位涨跌 ≤ −1% |

- 窗口：24h 单档。
- 面板结构：温度结论 + 关键数字（中位涨跌、涨/跌家数、异动家数）+ 涨跌榜（涨幅/跌幅 Top10，列：Binance 符号、24h 涨跌幅、窗口成交额）。人气、板块 v1 不做。
- 限速：全局共享保守限速器（见 Goal 随附范围）。
- 价格警报功能删除（见 Goal 随附范围）。

## Requirements

### A. 市场温度面板（核心）
- R1：以锚点为当前交易时刻、窗口 24h，对标的池每币计算涨跌幅；按广度+中位规则输出 5 档温度。
- R2：展示池中位涨跌幅、涨/跌家数、异动家数（默认 |24h 涨跌| ≥ 5%，阈值常量）。
- R3：涨跌榜各 Top10，行为 Binance 符号、24h 涨跌幅、窗口成交额；行内联动沿用选币结果表惯例。
- R4：面板可切入场/离场时刻，温度与榜随之重算。
- R5：池成员当时无行情、或复盘币无法归一进 Binance USDT-M 的，跳过并上报数量，不导致整体失败。
- R6：按锚点计算结果写入 candlestick 缓存复用；同锚点二次打开 0 请求；相邻锚点尽量命中缓存。
- R7：面板形态为明细头部浮层（与其他币/龙头同族）；打开态随交易切换自动更新锚点。
- R8：热度请求单币幂等、边拉边存；418/429 中断后重试只补齐缺失币。

### B. 全局共享限速器
- R9：抽出共享 Binance 请求节奏器（模块级单例），scan / 热度（及残留 Binance 消费者）统一 pace；间隔 ~100-120ms、保留 jitter 与并发上限。
- R10：`binanceRateGate` 的 429 退避 / 418 快速失败 + 警告透出行为保持不变，scan 与热度共用。

### C. 删除价格警报
- R11：删除上述价格警报全部代码、路由、UI、样式与对应测试；移除 `SERVERCHAN_KEY` 装配与 `notify.ts`；`price_alerts` 旧表不做迁移删除（无害残留，便于未来恢复）。

## Acceptance Criteria

- [ ] AC1（面板）：交割单与 Bitget 复盘明细头部可打开「市场温度」；锚点为入场时刻，可切离场。
- [ ] AC2（温度）：给出 5 档结论 + 中位涨跌、涨/跌家数、异动家数。
- [ ] AC3（榜）：Top10 涨幅 + Top10 跌幅，含 Binance 符号、24h 涨跌幅、窗口成交额；复盘币在池时可见/可定位。
- [ ] AC4（缓存）：同锚点二次打开不发起全池 K 线请求；相邻/推进锚点尽量命中已有缓存。
- [ ] AC5（降级）：历史无数据或复盘币无法归一时，面板仍给结论并上报跳过数量。
- [ ] AC6（标定）：温度门槛与异动阈值集中为常量。
- [ ] AC7（共享限速）：scan 与热度共用同一请求节奏器；scan 单次耗时按新间隔线性变化，且 429/418 处理与警告透出行为不回归。
- [ ] AC8（删除警报）：价格警报 UI/路由/后端/通知/测试全部移除，`npm test` 通过，无残留 import/引用（grep `alert|ServerChan|SERVERCHAN|价格警报|设警报` 仅剩无关命中）。
- [ ] AC9（回归）：交割单/Bitget 复盘、选币扫描、自由回溯主流程 `npm test` 全绿。
