# 复盘问题复现记录（11/14）

## 1. BTC 2020-08-03 最新回合需要两次平仓

### 真实数据

数据库：`data/review.sqlite`（只读查询）。

会话：`BTCUSDT / 2020-08-03 12:00`。回合 `position-10` 的两条平仓成交：

- `fill-12`：数量 `0.46107946739672284`，保证金 `536.2584745557584`，平仓价 `11568`，平仓时间 `1596831300000`。
- `fill-13`：数量 `5.551115123125783e-17`，保证金 `6.45622444395144e-14`，平仓价 `11748`，平仓时间 `1596880800000`。

第二条不是有意分批平仓，而是第一条 100% 平仓后留下的浮点尘仓。

### 确定性反馈回路

用真实会话的前三笔已实现盈亏重建权益，再以最新回合的真实参数调用生产函数：

- 方向 `short`，开仓价 `11630.5`，仓位比例 `50%`，杠杆 `10`。
- `openMarket` 得到数量 `0.4610794673967229`。
- 第一次 `closeMarket(..., 100)` 得到与数据库逐字段一致的 `fill-12`，并留下数量 `5.551115123125783e-17` 的单仓腿。
- 第二次 `closeMarket(..., 100)` 得到与数据库逐字段一致的 `fill-13`，仓位才归零。

根因公式（`src/ui/free-replay-paper-trading.ts:97`）：

```ts
position.quantity * normalizeCloseRatio(100) / 100
```

真实数量在该运算顺序下从 `0.4610794673967229` 变成 `0.46107946739672284`，少了 `5.551115123125783e-17`；`closeQuantityFor` 因此把仓腿剩余判断为 `> 0`。

限价路径也有同样入口（`src/ui/App.tsx:1107`）：`positionQuantity * closeRatioPercent / 100`。用同一数量构造 100% 限价平仓，复现相同尘仓。

额外边界：即使 `closeQuantity === position.quantity`，多仓腿场景也可能因逐项减法的舍入在最后一条仓腿留下约 1 ulp 的尘仓。随机数值探针快速找到反例，例如：

```text
legs = [946.8837696911233, 454.44114875185096]
position.quantity = 1401.3249184429742
last leg leftover = 1.1368683772161603e-13
```

所以修复不能只改 UI 的百分比公式；全平语义必须在 FIFO 平仓内部明确消费每条仓腿的全部剩余数量。
